# PLAYBOOK — сценарии контр-атак (fast-track)

Цель fast-track: чужой эксплойт, пойманный в трафике на нашем vulnbox,
должен принести флаги со ВСЕХ команд за минуты, пока флаг жив (п. 4.2 —
флаг действует 5 раундов, раунд 60 с).

Общий цикл: **перехват → детект (сервис + дедуп) → разметка в UI →
replay-кнопка на все команды → сдача → патч своего сервиса**.

## Рабочий режим через веб-интерфейс (основной)

Один процесс — UI, приём трафика и сабмиттер:
```sh
uv run --with fastapi,uvicorn,pyyaml python web.py --config config.yaml \
    --teams teams.yaml --with-ingest --with-submitter
# репетиция: добавить --dry (сабмиттер без реальной отправки)
```
Если vulnbox не может достучаться до ноутбука — параллельно запускается
poll-агент (сценарий 7).

Что вы видите в http://127.0.0.1:57020:

- **каждый новый эксплойт — одна строка-детект** с привязкой к сервису
  (порт → имя из `game.services`), счётчиком хитов, раундами, флагами и
  источниками. Повторы того же эксплойта (на новых флагах, в новых раундах)
  не создают шума. Другой шаблон, добывший ТОТ ЖЕ флаг в ТОМ ЖЕ раунде
  (другая команда exploiting ту же уязвимость), сливается с детектом как
  «вариант» — панель показывает обе формы payload;
- **NPC-автопроба**: новый пейлоад сразу проверяется на NPC (флаги NPC
  очков не дают — п. 4.7). Колонка NPC: `✓ N` — эксплойт рабочий и на N
  целей, `✗` — не сработал (нужен template-режим или это шум), `⏳` — идёт,
  `!` — NPC недоступен; кнопка ↻ в панели — перепроверка;
- **атрибуция флагов**: флаг, утёкший из вашего сервиса, прикрепляется к
  детекту — сразу видно, какие флаги уже утащили и в каком раунде;
- **клик по строке** — payload целиком, метка (exploit/noise/patched),
  заметка и кнопки replay: на все команды (verbatim/template) и ↻ на NPC;
- флаги из любого replay автоматически уходят в очередь сабмиттера;
- фильтры по сервису и метке, автообновление каждые 5 с.

Рабочий цикл в игре: смотрите ленту детектов → новый детект ждёт NPC-статус
(`✓` = чужой эксплойт рабочий, реплай немедленно; `✗` = смотрите payload,
вероятно нужен template — сценарий 2, или это шум → метка noise) → replay
на все команды → сабмиттер сдаёт → патчьте свой сервис.

CLI-путь (extract/replay) остаётся для случаев, когда атака найдена не в
live-ленте, а ретроспективно в pcap (сценарий 5).

## Сценарий 1. HTTP-эксплойт на витрине (самый частый)

Что видно: чужой HTTP-запрос целиком (GET/POST с инъекцией или gadget).

1. В UI появился детект сервиса с preview запроса → клик → payload целиком.
2. Жмёте **«запустить на все команды»** (verbatim). Успех: флаги в панели,
   сабмиттер их сдаёт. Время: <1 минуты.
3. Если `flags=0` на всех целях — проверьте payload на team-specific
   маркеры → сценарий 2.

CLI-эквивалент:
```
uv run --with pyyaml python extract.py laptop/pkappa2-ingest/cap_*.pcap \
    --checker-ips <IP_ЧЕКЕРА> --payload 1 --out /tmp/p.bin
uv run --with pyyaml python replay.py --payload /tmp/p.bin \
    --teams teams.yaml --config config.yaml --submit
```

## Сценарий 2. Параметризованный эксплойт (team-specific)

Признаки: в payload есть ваш флаг, session-id, uuid, hex-токен. Дедуп уже
работает на вас: такие запуски схлопываются в один детект, а значения
выносятся в плейсхолдеры `{FLAG}`, `{UUID}`, `{HEX32}`, `{HEX64}` (видны в
панели детекта как template).

1. В UI переключаете режим replay на **template** и запускаете.
2. Плейсхолдеры рендерятся пусто — обычно достаточно, потому что эксплойт
   читает свежий флаг на каждой цели. Если нужен подставной флаг (эксплойт
   печатает флаг только при сравнении) — подставьте свой текущий флаг руками.

Время: 1–2 минуты.

## Сценарий 3. Не-HTTP протокол (raw TCP / бинарный)

`GETFLAG`-подобные команды ловятся как `raw`-детекты того же сервиса.
В UI — тот же цикл: клик → payload (hexdump-вью там же) → replay
(`replay.py` шлёт сырые байты в сокет и читает ответ до таймаута).
Для интерактивных протоколов (запрос-ответ-запрос) допишите диалог в
`adtool/replay.py:send_payload` по аналогии (последовательные sendall/recv).

Время: 1–2 минуты.

## Сценарий 4. Эксплойт виден только в ответе

Некоторые атаки проявляются не в запросе соперника, а в изменении ответа
вашего сервиса чекеру (инъекция в хранилище, отравление кэша).

Метод: дифф ответов чекера. В `analyzer` проверочный трафик помечен как
`checker`. Откройте pkappa2 (http://127.0.0.1:2812), найдите потоки к вашему
сервису и сравните ответ чекера «до» и «после» атакующего запроса — лишние
данные в ответе укажут на примитив. Затем воспроизведите примитив сами
(обычный ручной эксплойт) и реплайте через сценарий 1/2.

Время: 3–10 минут — поэтому сначала всегда пробуйте сценарии 1–2.

## Сценарий 5. Ретроспектива (атаку заметили поздно)

Флаги живут 5 раундов — успеваете добрать. pkappa2 ищет полнотекстом по всем
pcap из `pkappa2-ingest/`:

- поиск по regex флага `[A-Z0-9]{31}=` — все флаги, ходившие в трафике;
- поиск по имени эндпоинта, который вы подозреваете;
- поиск `ATTACK`-маркеров не нужен — pkappa2 ищет по сырым байтам.

Добытые из чужого эксплойт-запроса флаги чужих команд тоже валидны — сдайте
их (source=traffic), пока не истёк срок.

## Сценарий 6. Приоритеты в игре

1. Первые 10 минут после старта: web.py (--with-ingest --with-submitter)
   запущен; в UI проверочные запросы чекера НЕ создают детектов (else — IP
   чекера указан неверно), сервисы в детектах определяются правильно (else —
   заполните `game.services`), NPC-проба даёт статусы (else — проверьте
   npc-цель в teams.yaml).
2. Держите вкладку UI на виду: новый детект с `✓` в NPC = чужой эксплойт
   рабочий — реплайте немедленно, потом патчьте свой сервис (п. 6.1 — патч
   обязан сохранять функциональность, иначе MUMBLE/SLA). Детект с `✗` —
   попробуйте template-режим или пометьте noise.
3. Патч и реплай параллельно: сначала реплай (флаги имеют срок), потом патч.
4. Размечайте: `exploit` — рабочий эксплойт, `noise` — сканеры/мусор,
   `patched` — уже закрыли у себя. Фильтр по метке экономит время.
5. Каждый ~5 минут сверяйте счётчик уникальных флагов в шапке UI с объёмом
   собранного — сабмиттер дедупит, повторные сдачи не тратят квоту.

## Сценарий 7. vulnbox не может достучаться до ноутбука (poll-режим)

Признаки: pcapstream на vulnbox молчит / `[pull]` не появляется в
ingest; с vulnbox `nc -z <IP_ноутбука> 57012` не проходит. Причина —
нет маршрута от соревновательной сети к ноутбуку или firewall на ноутбуке.
SSH в обратную сторону (ноутбук → vulnbox) доступен всегда (п. 3.1).

Переключение на poll (30 секунд):
1. На vulnbox остановите live-стрим и запустите файловый capture
   (`vulnbox/capture.py`, имена `r{раунд}_p{part}_{ЧЧММСС}.pcap`, окно 20с):
   docker: `GAME_START=<epoch> docker compose up -d capture`
   (без python3 на vulnbox — fallback `sudo ./vulnbox/capture.sh`).
2. На ноутбуке: poll-агент (docker: `VULNBOX=root@<vulnbox-ip> docker compose
   --profile pull up -d`; или вручную `./laptop/pull.sh root@<vulnbox-ip>
   http://127.0.0.1:57013/pcap 10`) — агент по rsync забирает файлы и заливает
   их в web.py; повторно не шлёт (state в `pull-state/` или `~/.ad-pull/`).
3. Задержка live-детекта — до ~1 раунда (файл отдаётся после стабилизации,
   чтобы не грузить недописанный pcap). Флаг живёт 5 раундов (п. 4.2) —
   fast-track всё ещё успевает.

Проверьте ДО игры: ssh-ключ на vulnbox без пароля, rsync/curl доступны
в контейнере poll-агента (ставятся автоматически); репетиция сценария на demo.

## Чек-лист подготовки (до зачётного старта)

- [ ] `config.yaml`: адрес ForcAD, токен, `checker_ips`, `game.services`
      (порт → имя каждого своего сервиса), `game.start`
- [ ] `teams.yaml`: NPC-цель (`npc: true`) для автопроби, адреса всех команд
      + порты всех сервисов, disabled-записи где нужно
- [ ] webui запущен (docker compose или web.py --with-ingest --with-submitter)
- [ ] канал vulnbox → ноутбук: либо pcapstream (live), либо pull (poll,
      сценарий 7) — проверить оба до игры; в capture передан GAME_START
- [ ] pkappa2 доступен, файлы из ingest видны в UI
- [ ] сабмиттер в режиме dry один прогон: очередь → батч без ошибок
- [ ] отрепетирован сценарий 1 на timе: цель — от нового детекта в UI до
      «флаги в очереди» за 60 секунд

## Границы регламента (проверять перед каждым действием)

- Атаки — только с личного ноутбука (п. 3.6); с vulnbox реплаи не делать.
- Никаких DoS/DDoS и мусорного трафика (п. 8.5): replay шлёт ОДИН запрос
  на цель; не зацикливать.
- Не атаковать инфраструктуру организаторов (п. 8.6): в teams.yaml только
  адреса сервисов соперников из брифинга.
- Патчи — с сохранением функциональности (п. 6.1–6.2), без WAF/прокси (п. 8.9).
